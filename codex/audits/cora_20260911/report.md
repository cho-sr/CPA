# CoRA / 최근 zero-fill baseline 관측값·통신량 점검

점검일: 2026-09-11. 사용자가 지정한 최근 zero-fill baseline과 CoRA(R=8)를
대조했다. 기존 실험 파일은 변경하지 않았고, 학습·CPA·FIA를 새로 실행하지
않았다. 저장 파일의 읽기, 해시 검증, CPU 디코딩과 후보 입력 재생성만 수행했다.

**결론: 유지율 80%·50%·30%는 동일한 수치 관측값을 이용하는 비교로 확인됐다.
유지율 10%의 최근 zero-fill baseline과 기존 CoRA는 관측값과 체크포인트가
달라 동일 조건 비교로 사용할 수 없다. 희소 관측 파일 자체의 바이트 절감은
확인됐지만, 전체 FedAvg 통신의 네트워크 실측은 구현되어 있지 않다.**

## 찾아낸 코드와 실험 조건

- 현재 구현: [CoRA_sparsification.py](../../../cora_fedavg_single_client_cpa/CoRA_sparsification.py).
- 최근 baseline 실행 파일: [80/50/30% zero-fill](../../../cora_fedavg_single_client_cpa/run_cora_observation_zero_fill_keep80_50_30.bat),
  [10% zero-fill](../../../cora_fedavg_single_client_cpa/run_cora_observation_zero_fill_keep10_e920.bat).
- 관측은 `S_r(theta_local - theta_before_round)`이며, 실제 SGD 이후와 이전의
  파라미터 차이다. `common.py:265`에서 실제 모델 파라미터를 빼고,
  `CoRA_sparsification.py:380`의 SGD 수집 결과에 Top-k를 적용한다.
- VGG16, 3개 클라이언트, 라운드20 시작 체크포인트, 관측 대상 client0,
  24장, 로컬 SGD **1스텝**, lr=0.001. 모멘텀·weight decay=0.
  이 CoRA 실험은 최근 same80의 n16/T10 실험과 별도 조건이다.
- Top-k는 **모든 모델 파라미터를 합친 전체 업데이트**에 적용하고, 그중
  `classifier.0.weight` (4096×25088)를 공격한다. 따라서 전체 유지율50%와
  FC1 유지율50%는 다르다. 실제 전체 파라미터 수는 138,357,544개다.
- 서버의 전체 라운드 집계가 아닌, 집계 전 단일 클라이언트의 압축 업데이트를
  관측한다. 라운드 모델은 클라이언트별 희소 업데이트의 가중평균으로 갱신한다.

## 관측값 대조

| 전체 업데이트 유지율 | 최근 zero-fill / CoRA 대조 | 판단 |
|---|---|---|
| 80% | 파일 해시는 달라졌지만 전체 수치 업데이트 해시·체크포인트가 동일. 보존된 shared-FP32 사본으로 확인했고, 양쪽 실제 후보 입력 해시도 재현됨 | 수치 관측값 동일, 원본 파일의 바이트 단위 보존은 불완전 |
| 50% | 원본 파일·관측 인덱스·체크포인트 해시 동일, NPZ 디코딩 및 양쪽 실제 후보 입력 해시 재현 | 동일 관측값 확인 |
| 30% | 원본 파일·관측 인덱스·체크포인트 해시 동일, NPZ 디코딩 및 양쪽 실제 후보 입력 해시 재현 | 동일 관측값 확인 |
| 10% | baseline은 `e920201510be97a8`, CoRA는 `5441531bedd12a66`; 체크포인트·원본 FP32 해시·관측값이 다름 | 동일 조건 비교 불가 |

10%의 두 실행은 사진 ID는 같지만 local micro-batch가 baseline4 / CoRA24로
다르며 체크포인트도 다르다. FC1 관측값의 서로 다른 원소는 **3,683,060개**,
baseline 관측값을 분모로 한 상대 L2 차이는 **0.0515878897 (5.16%)**다.
이는 메타데이터만 다른 경우가 아니다. 이 차이가 어떤 개별 구현/수치 요인으로
생겼는지까지는 이번 읽기 기반 점검으로 인과적으로 분리하지 않았다.

80%는 보존된 shared-FP32 사본과 현재 전체 업데이트 모두 해시
`b5a99e7d173bf10cdc8e7f0348bb0edffac086bc5e1e552af7c08f8be395f255`
이며 모든 원소의 수치가 같다. tau=0이라 CoRA의 누락값 추정도 0이다.
현재 원본/관측 인덱스 파일 해시는 기존 CoRA 기록과 달라졌으므로, 기록 파일의
완전한 불변성을 주장할 수는 없다.

50%에서는 보존된 재생성 dense 업데이트 해시가 원래 수집 시 기록한 FP32
업데이트 해시와 일치했다. 유지된 FC1 값은 이 실제 dense 값과 **FP32 비트까지
동일**하며, 버린 값의 최대 절댓값과 tau는 3.725290298461914e-09다.
FC1의 희소화 상대 L2 오차는 **0.00240581 (0.2406%)**다. 따라서 최근 same80
Top-k50에서 발견한 손실0이라는 결론을 이 CoRA 실험에 적용하면 안 된다.

## 실제 직렬화 크기

실제 NPZ는 **선택된 FP32 값 + packed 위치 비트맵 + shape**를 저장한다.
수신 함수는 비트맵을 풀어 위치를 얻고, zero-fill은 나머지를0으로 복원한다.
아래는 실제 디스크 크기를 읽은 NPZ에 관측 인덱스 pickle까지 포함한 값이다.
비교 기준은 동일 FC1의 dense FP32 값 411,041,792 bytes (411.04 MB)다.
MB는 10^6 bytes이며 공용 모델/이미지는 이 관측 payload 계산에 넣지 않았다.

| 전체 유지율 | FC1 실제 유지율 | NPZ+관측 인덱스 bytes | MB | FC1 dense 대비 절감 |
|---|---:|---:|---:|---:|
| 80% 현재 파일 | 73.0947% | 313,299,132 | 313.30 | 23.78% |
| 50% 양쪽 동일 관측 | 43.4920% | 191,619,816 | 191.62 | 53.38% |
| 30% 양쪽 동일 관측 | 21.5107% | 101,267,392 | 101.27 | 75.36% |
| 10% zero-fill | 4.0381% | 29,447,756 | 29.45 | 92.84% |
| 10% CoRA | 4.0345% | 29,432,888 | 29.43 | 92.84% |

각 NPZ의 shape/컨테이너 오버헤드는798 bytes, 관측 인덱스는3,466 bytes다.
동일 관측을 쓰는 경우 CoRA는 받은 패킷으로 서버 측 후보를 여러 개 만들기
때문에 R=8이 클라이언트 업로드8회를 뜻하지 않는다. 통신량은 baseline과
같고 공격 계산량이 늘어난다.

이 크기는 **공격 대상 FC1 관측 파일의 실제 직렬화 크기**다. 학습 루프는
`sparse_update_and_masks`에서 `pack_masks=False`로 dense zero-filled 딕셔너리를
만들고 `add_weighted_update_`로 메모리에서 합산한다. 모든 클라이언트·모든
라운드의 전체 모델 패킷을 직렬화해 전송·수신하는 경로는 이 코드에 없다.
원본 `.pickle`은 이미지와 평가용 정보까지 포함하는 약570.3 MB의 dense
실험 캐시이므로, 이를 압축된 전송 패킷으로 계산하면 안 된다.

전체 모델을 FP32 값+비트맵으로 전송한다고 **가정**하면 오버헤드 제외 예상
절감은 keep80/50/30/10에서 각각 약16.875/46.875/66.875/86.875%다.
이는 구현된 전체 모델 전송의 측정값이 아니다. 네트워크 속도나 지연 감소도
이번 기록만으로 주장할 수 없다.

## 공격 입력과 평가 정보

각 관측 shard의 값·마스크 해시를 재계산하고,0을 채워 복원한 FC1이 저장된
희소 업데이트와 모든 원소에서 같은지 확인했다. 서로 다른5개 소스 모두 통과했다.

현재 파일의 순수 CPU `sample_missing_values` 함수를 사용해 최근 baseline4개와
최종 선택 CoRA 후보4개의 공격 입력을 재생성했다. **8개 모두 기록된
`update_tensor_hash`와 일치**했다. 모든 후보에서 관측된 값은 FP32 비트까지
그대로 유지되고, 생성된 누락값은 tau 범위 안에 있었다. 선택 CoRA 후보는
keep80/50/30/10 순서로 member6/0/4/0이다.

코드상 CPA는 이 재생성 FC1을 사용하며, FIA에는 CPA 추정 임베딩의 절댓값을
넣는다. 정답 이미지·임베딩은 FIA 이후 평가에 사용한다. CoRA 후보 순위는
재구성 이미지의 모델 예측 라벨로 업데이트를 다시 만들어 관측과 비교한다.
원래 버린 실제 값을 후보 생성에 넣는 경로는 확인되지 않았다.

다만 실험 캐시와 관측 인덱스에는 sample ID/평가용 정보가 함께 존재하므로,
이 저장 구조 전체를 격리된 네트워크 수신 프로세스라고 해석하면 안 된다.
여기서 검증한 것은 실제 공격 입력의 데이터 의존성과 직렬화된 희소 관측이다.
또한 CoRA는 다중 CPA/FIA 및 screening을 수행하므로 baseline과 계산 예산은
동일하지 않다. 이번 관측값 일치 검증이 동일 계산 예산을 뜻하지는 않는다.

## 재실행 경로 문제

현재 본체는 `CoRA_sparsification.py`인데, 관련 `.bat` 파일과
`prepare_shared_fp32_topk.py`의 import는 삭제된
`run_cora_fedavg_single_client_cpa.py`를 여전히 참조한다. 따라서 현재 상태로
해당 명령을 그대로 재실행하면 파일/모듈 경로 오류가 난다. 이 점은 저장된
결과에 대한 수치 검증과 별개이며, 이번 요청에서는 실행 코드를 수정하지 않았다.
